# 面试项目表达

## 一句话版本

我把一个最初偏探索性的电商购物车流失项目，重构成了以“首次加购后 48 小时会话—商品结果”为核心的可复现分析链路，并用 SQL、Python、Excel 和 Power BI 口径对账，最终将品牌结论从因果化的“风险品牌”收紧为可执行的“运营排查优先级”。

## 90 秒版本

这个项目使用 2019 年 12 月约 353 万条美妆电商事件，目标是回答：用户加购后没有购买时，运营应该先排查哪些品牌。

我复盘旧版本后发现，最大的风险不在模型，而在口径：一行数据究竟代表用户、会话还是商品不够统一；月末样本没有完整观察期；`NaN` 字符串可能被当作真实会话或品牌；旧模型还使用了结果发生后的 session 行为，存在目标泄露。

因此我把主粒度固定为“有效会话内某商品的首次观测加购”，只保留完整 48 小时观察窗口，并构造互斥的 A/B/C 结果：购买、无购买且无移除、未购买但移除。正式队列有 772,119 个样本，总体购买率 13.56%，66.22% 在窗口内没有明确结果，移除率 20.22%。这说明不能只在 A+C 子样本中报告 40.14% 的明确结果购买率。

品牌层面只有 55.99% 的样本品牌已知，所以我没有把品牌排名写成全站根因，而是用覆盖量和移除/购买比做排查优先级。`grattol`、`masura` 等品牌进入第一批核查，但下一步必须下钻 SKU 并联查库存、促销、运费和结账错误。

最后我把 SQL 拆成可验证步骤，用 Python重新聚合并完成 25 项对账，交付了正式 Notebook、Excel、管理层报告、Power BI DAX 和复现说明。这个项目让我最重要的收获是：分析价值首先来自正确的粒度、窗口和证据边界，而不是更复杂的模型。

## 3 分钟结构

### 1. 业务问题

不是泛泛地做用户行为分析，而是帮助运营决定：购物车流失排查资源有限时，哪些已知品牌应该先被下钻检查。

### 2. 关键口径

- 一行：`user_session × product_id` 的首次观测加购。
- 观察窗口：加购后 48 小时，必须完整。
- A：窗口内购买；C：无购买但移除；B：两者都没有。
- 主指标：A/(A+B+C)。A/(A+C) 只表示明确结果样本的购买率。

### 3. 最难的问题

最难的不是 SQL 语法，而是发现并修复口径偏差：月末右截断、占位字符串、品牌缺失、不同工具对 NULL 的处理差异，以及旧模型的事后特征泄露。

### 4. 结果

- 正式队列：772,119。
- 购买率：13.56%；未明确处置率：66.22%；移除率：20.22%。
- 已知品牌覆盖率：55.99%。
- 48 小时结论在共同 24/48/72 小时队列上较稳定；购买率极差仅 0.043 个百分点。
- 20 个品牌达到本项目的“高覆盖量 + 高移除/购买比”启发式条件。

### 5. 建议与边界

先下钻优先品牌的 SKU，再核查库存、费用/配送展示、促销一致性和错误日志。现有数据只能给排查顺序，不能证明品牌造成流失；真实干预效果需要补字段或实验。

### 6. 交付

只读 SQL、Python 对账、可执行 Notebook、Excel、管理层报告、Power BI 页面/DAX 规范、数据与指标字典、数据质量报告和复现说明。

## 高频追问与回答要点

### 为什么粒度不是用户？

因为业务事件发生在某次会话中的某个商品上。同一用户可能在多个会话加购多个商品；直接聚合到用户会混合不同商品和时间窗口。用户级指标可以另算，但不能与会话—商品指标共用分母。

### 为什么选择 48 小时？

48 小时是一个可解释的短期运营窗口，并通过同一批完整 72 小时样本做了 24/48/72 小时敏感性检查。总体购买率只变化 0.043 个百分点，所以主结论对这三个窗口不敏感；它仍不是行业统一标准。

### 为什么购买优先于移除？

同一窗口可能先移除后又购买。业务结果以是否成交为优先；否则一个最终购买样本会被错误归为主动流失。规则写入 SQL，并验证三组互斥且总和等于队列。

### 为什么不删除重复行？

原始数据没有稳定 `event_id`。按业务字段观察到 183,860 个重复超额行，但这些可能包含真实的重复行为；没有技术主键时直接删除会引入另一种偏差，所以只披露并在后续数据采集中要求事件 ID。

### “移除/购买比”为什么不是风险概率？

它是 C/A，可以大于 1；概率应该有明确事件和分母并落在 0 到 1。这个比值适合排序，但不能说成某品牌有多少概率导致流失。

### 品牌结论能否用于减少曝光？

不能直接执行。品牌只有 55.99% 覆盖，而且没有库存、促销、运费和错误信息。第一步应下钻 SKU 和补充机制数据；减少曝光属于干预，需要评估 GMV、用户体验和品牌合作等成本。

### 为什么不继续做模型？

旧模型的高分主要受事后 session 特征影响，修复泄露后性能明显下降。当前决策是确定排查优先级，不需要预测模型；先完成口径和交付比堆模型更有价值。如果未来有实时干预场景，再定义预测时点和可用特征。

### 如何证明 SQL 和 Python 一致？

SQL 从原始表构建正式队列并导出明细；Python不复用 SQL 汇总值，而是从明细重新按 A/B/C 和品牌聚合，再比较总量、分组、比率和品牌结果。25 项检查为 0 个错误。

## 诚实描述个人与 AI 的分工

推荐说法：

> 我负责业务问题、口径理解、结果验收和最终表达；在重构过程中使用 AI 协助审计旧文件、生成部分 SQL/Python/文档草稿和执行检查。我重点验证了数据粒度、时间窗口、标签逻辑、跨工具对账和结论边界，并能解释正式链路中的输入、输出和关键 SQL。

不推荐说法：

> 所有代码和报告都是我完全独立从零手写的。

面试前至少能现场解释：`first_cart`、完整窗口过滤、`BOOL_OR` 标签、A/B/C 优先级、品牌分子分母、共同窗口队列和 Python 对账逻辑。
